## What Spinel is

- A whole-program ahead-of-time compiler. It parses Ruby with libprism, infers a static type for every value across the whole program, emits one C file, and calls the system `cc` to build a standalone native executable (`README` [L1-47](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/README.md#L1-L47)).
- The compiled binary carries no Ruby interpreter. Generated binaries need only libc and libm, plus any system library a package binds, such as libssl or libsqlite3 (`README` [L568-574](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/README.md#L568-L574); `SPIN` "What a pack cannot carry").
- `LIMITS` puts it in one line: there is no Ruby interpreter, parser or type-inference engine in the running program ([L3-7](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/docs/limitations.md#L3-L7)). Every limit below follows from that.

**How failures show up.** A construct the compiler rejects stops the build. It prints `spinel: FILE:LINE: ...`, one line per refusal, and writes no binary. Some constructs compile and then raise `NotImplementedError` or `NoMethodError` only when the code runs. `--defer-refusals`, or the magic comment `# spinel: defer-refusals` at the top of a file, turns eligible compile-time refusals into runtime raises. Per the docs, a successful compile "does not establish CRuby-compatible behavior" (`LIMITS` [L20-43](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/docs/limitations.md#L20-L43)).

## Stdlib

`require` is resolved when the program is compiled. Each require splices in Ruby source; nothing searches directories at run time. `$LOAD_PATH` starts empty, and changing it loads nothing new. A `require` that Spinel cannot satisfy is a compile error under `--strict-require`, which `spin build` always turns on. Libraries Spinel does not implement include `ripper`, `objspace` and `coverage` (`REQUIRE` [L15-37, L113-130](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/docs/require.md#L15-L37)). The bundled libraries live in [`packages/`](https://github.com/matz/spinel/tree/afe2a920fd66fb9e16df7b3356f9cf29b4546418/packages): abbrev, base64, benchmark, bigdecimal (subset), cgi, csv, date, did_you_mean, digest, erb, etc, ffi, fiddle, fileutils, find, forwardable, getoptlong, io, ipaddr, json, logger, net (http, smtp), observer, open3, openssl, optparse, pathname, pp, prettyprint, psych, pty, racc, resolv, rexml (subset), securerandom, set, shellwords, singleton, sqlite3, stringio, strscan, syslog, tempfile, time, timeout, tmpdir, tsort, unicode_normalize, uri, weakref, yaml, zlib.

## Gems and C extensions

- **No RubyGems at run time.** Spinel is not installed as a gem. A third-party library is a *source tree* that gets compiled into the binary. You either point at it with `-I <dir>`, where `require "x"` resolves to `x.rb` or `x/x.rb`, or let the `spin` tool resolve it from `spin.toml`. `spin.toml` accepts a `path`, a `git` URL, or a version constraint against the git-hosted index [matz/spin-index](https://github.com/matz/spin-index). Version selection is minimal version selection (the lowest release that satisfies the constraint), and `spin.lock` pins the commit (`README` [L77-91](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/README.md#L77-L91); `SPIN` [L113-150](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/docs/spin.md#L113-L150); `REQUIRE` "Providing your own feature").
- **A gem works only if its Ruby fits the subset.** Gems that lean on metaprogramming usually fail to compile (`LIMITS` [L107](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/docs/limitations.md#L107)). The README points to a community survey of which gems compile, [OriPekelman/spinelgems](https://github.com/OriPekelman/spinelgems), and a RuboCop cop that flags unsupported code, [gurgeous/rubocop_spinel](https://github.com/gurgeous/rubocop_spinel) (`README` [L628-657](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/README.md#L628-L657)). Both are community projects, not matz's. Ticket 02 covers them.
- **A `-I` root takes priority over the bundled packages.** A project can therefore ship its own fork of a bundled library, such as `psych` (`REQUIRE` "Providing your own feature").
- **There are three ways to use C:**
  1. **FFI**: `ffi_func` and `ffi_lib` declarations in a `module` compile to direct C calls against a system library ([docs/FFI.md](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/docs/FFI.md)).
  2. **C carried in a package**: `.c` files listed in `[package] sources` are compiled once into a cache and linked in, then bound through FFI (`SPIN` [L241-319](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/docs/spin.md#L241-L319)).
  3. **A C extension layer (issue #7210)**: a gem's own `ext/*.c` is compiled *from source* against a **restricted `ruby.h` that is "not the CRuby ABI"** ([include/ruby.h L1](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/include/ruby.h#L1)). It is declared in a package's `[cext.*]` table. The bundled `sqlite3` (sqlite3-ruby 2.9.5) and `racc` (1.8.1) packages are built this way ([packages/sqlite3/spin.toml](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/packages/sqlite3/spin.toml), [packages/racc/spin.toml](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/packages/racc/spin.toml); [docs/internals/cext-recorder.md](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/docs/internals/cext-recorder.md); `LIMITS` [L351-362](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/docs/limitations.md#L351-L362)). **Prebuilt `.so` or `.bundle` extensions cannot be loaded.**
- `spin ext` goes the other way. It compiles a Ruby kernel written in the subset into a CRuby native-extension gem (`SPIN` [L539-583](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/docs/spin.md#L539)). That is not relevant to Ebenezer's shipped binary.

## Toolchain and build commands

- **Building Spinel:** `make deps` fetches libprism from the prism gem tarball on rubygems.org, then run `make`. `sudo make install` is optional, and `make install PREFIX=$HOME/.local` installs elsewhere. Other targets: `make test`, `make bench`, `make clean`. A release tarball (`spinel-<release>.tar.xz`) bundles the parsers and builds offline (`README` [L49-75](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/README.md#L49-L75), [L489-511](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/README.md#L489-L511)). CRuby is needed only as an optional parser fallback and for the test harness ([L509-511](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/README.md#L509-L511)).
- **Compiler CLI:**
  - `spinel app.rb` compiles to `./app`; add `-o out` to name the binary.
  - `-c` emits C only; `-S` prints the C to stdout.
  - `-E app.rb args` compiles, runs and discards the binary; `-e 'code'` compiles inline source.
  - `--incremental` caches C units for development builds; release builds stay one unit.
  - Other flags: `--int-overflow=`, `--rbs DIR`, `--strict-require`, `--defer-refusals`, `--debug` and `-g`.
  - `spinel diff app.rb` runs a program under both CRuby and Spinel and reports the differences.

  (`README` [L93-138](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/README.md#L93-L138), [L583-608](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/README.md#L583-L608))
- **Project tool `spin`** (cargo-like):
  - Scaffolding and running: `spin new`, `spin run`, `spin build`, `spin install` (installs to `~/.local/bin`).
  - Dependencies: `spin add`, `spin remove`, `spin list`, `spin tree`.
  - Tests: `spin test`, which takes snapshot tests with CRuby as the reference.
  - Sharing: `spin publish`, and `spin pack`, which writes a C-only build directory with a Makefile that needs only `cc` and `make`.

  `spin` compiles with strict require always on (`SPIN` [L1-100](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/docs/spin.md), [L421-488](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/docs/spin.md#L421-L488)).
- **C compiler requirement:** the C must be compiled by gcc or clang, because the runtime uses `__attribute__((cleanup))`, statement expressions and `__typeof__`. A strict ISO C compiler will not work (`SPIN` "Shipping a build"; [docs/portability.md](https://github.com/matz/spinel/blob/afe2a920fd66fb9e16df7b3356f9cf29b4546418/docs/portability.md)).
- **Compile speed:** whole-program inference means `spin` has no per-file incremental mode, but per the docs compiles are fast (`SPIN` "Rebuilds"). The README says a compiled binary starts in about 0.8 ms (`README` L185-186).

## Target platforms

| Platform | Status |

## Implications for Ebenezer

1. **File I/O and directory walking are fine.** `File.read`/`write`/`binread`, `Dir.glob` and `children`, `FileUtils.mkdir_p`/`cp`/`rm_rf`, `File.mtime` and `File.stat` cover reading a source tree and writing `_site/`. Copy binary assets with `File.binread` or `IO.copy_stream`; binary strings are a supported encoding. Do not use `File.read(path, mode: ...)`.
2. **Assume UTF-8 for all content.** Source files in Latin-1, Shift_JIS or UTF-16 cannot be transcoded. A UTF-8 BOM cannot be stripped through `set_encoding("BOM|...")`, so strip `\xEF\xBB\xBF` by hand. Document UTF-8 as a requirement.
3. **Plan for frozen string literals.** Build output with `+""` or `String.new` and then `<<`. Strings are fast: the README benchmarks list a template engine at about 5.9x and str_concat at about 4.6x faster than YJIT.
4. **Regex is good enough for Markdown and front matter.** It has lookaround, named groups and Unicode classes. Keep any single pattern under 32 capture groups, and expect `RegexpError` rather than silent failure when a pathological backtracking pattern runs on a huge input. User-configured patterns can use `Regexp.new` at run time.
5. **YAML front matter works, with one sharp edge: dates.** Unquoted `date: 2024-01-01` or `2024-01-01 10:00:00` raises `DisallowedClass` under `safe_load`, and **`NotImplementedError` if Date or Time is permitted**. Jekyll front matter often contains such dates. Options:
   - Ebenezer vendors a patched `psych` through a `-I` root that returns those scalars as Strings, then parses them with `Time`.
   - Write a small purpose-built front-matter parser.
   - Require dates to be quoted, which is weaker for Jekyll compatibility.

   Anchors, aliases and `!ruby/object` tags beyond the basics are also unavailable. This feeds ticket 06.
6. **ERB is out, and Liquid-as-gem is doubtful.** ERB templates need `eval`, so Ebenezer must ship a **template language interpreted at run time**: a parser and evaluator written in the subset, for example a Liquid subset. User templates are data, not Ruby. Filter and tag dispatch should go through explicit Hash or `case` tables rather than `send` with computed names or `method_missing`-backed drops. Static `send` dispatch over a closed set works but widens to boxed (poly) values. This feeds ticket 05.
7. **No plugin system in user-supplied Ruby.** Without `eval` or runtime `require`, Jekyll-style `_plugins/*.rb` cannot be loaded into the shipped binary. Plugins would need a recompile, a subprocess protocol (`system`, `Open3`, `Process.spawn`), or a data-only extension model. This is a product decision for v1.
8. **Markdown needs its own plan.** No Markdown library is bundled. Options: pure-Ruby Markdown written in the subset; kramdown or redcarpet ported, if the survey (ticket 02) says they compile; or cmark's C sources carried in a package (`sources = [...]`) and called through FFI. The C route is likely the most robust, since packages can carry C.
9. **A dev server is feasible.** `TCPServer` plus threads with no GVL can serve `_site/` over HTTP/1.1. Ebenezer must write the small HTTP layer itself, because there is no WEBrick or Rack. Live reload by file watching has no inotify or FSEvents binding and no `listen` gem, so poll `File.mtime` from a thread, or bind inotify or kqueue through FFI. WebSocket live-reload would also be hand-written.
10. **Errors in a release build have no backtraces.** `Exception#backtrace` is `[]`. Ebenezer should give its own errors context (file and line of the template or front matter) and not rely on Ruby backtraces. Use `--debug` builds while developing.
11. **Distribution.** Ship native builds for Linux x86-64/arm64 and macOS Intel/arm64, which are the CI-covered platforms. Windows means WSL. Each target needs its own build host or a cross-`cc` via `spin pack`. The binary depends only on libc and libm unless openssl or sqlite3 is used, so avoid those to keep it standalone.
12. **Write the code inside the subset from day one.** Develop with `spin test` (CRuby as reference) and `spinel diff`, and lint with `rubocop_spinel`. Avoid the metaprogramming Jekyll's codebase uses: `method_missing` drops, `define_method` with computed names, and `instance_variable_get` with computed names.

## Uncertainties and open points

- **Nothing was compiled.** Every claim comes from the docs and source at `afe2a92`. The YAML date behaviour, the ERB behaviour, the socket server and `Dir.glob` should be smoke-tested in ticket 04.
- **The `[cext.*]` C extension layer** is used by bundled packages, but no user-facing doc describes it. Only internals docs and package manifests do. Whether third-party packages are meant to use it, and how stable it is, is unclear.
- **The README is partly stale:** the test and benchmark counts disagree, and the "No encoding" bullet is vaguer than `LIMITS`. Where they conflict, `docs/limitations.md` is the more detailed and apparently current source.
- **Exact per-method coverage** of String, File and Dir was not enumerated. I inferred it from method-name strings in `src/*.c` and from docs mentions. Refusals are per call, so the real test is compiling Ebenezer's code.
- **Compile times** for a project of Ebenezer's size were not measured.
- **No statement from matz outside the repo** (talks, interviews) was used. The repo docs were treated as the author's statements.
